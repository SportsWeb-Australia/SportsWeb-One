Standard Operating Procedure

SportsWeb One — Build-from-Scratch SOP

Onboard a NEW club: content from an old site (if any) and/or design from inspiration sites + screenshots.

Law = SPORTSWEB-WEB-STANDARDS.md (S1–S20). Sits alongside SPORTSWEB-LIVE-MIGRATION-SOP.md (which is a like-for-like cutover) — this one is for a fresh build, where the design and/or the content come from elsewhere.

Written for the Builder, not the Club Editor. This SOP is for Carson + Codey operating with full API/DB access to onboard a club. It is not the guide a volunteer uses in the platform's Club Editor to maintain their own content day to day.

Default end-state = a fully onboarded club inside the existing SportsWeb One app — not a new repo or deployment. Every club renders through the one shared app (sportsweb-one-club-template), resolved by domain (src/App.tsx); PageRenderer.tsx walks the club's published_layout/draft_layout fetched via the public_club_page RPC (usePublicClubPage.ts). However the content and design are sourced, the finished result is the club's content loaded into the platform's editable fields via the admin Import a club tool / SiteMigrations.tsx, and the owner edits it through the platform editor from then on. There is no per-club codebase, build, or hosting choice to make. Do not ship content baked into static HTML as the default — that's not editable by the club.

🔴 Before writing any page, run the Pre-flight design check (SPORTSWEB-EDITABLE-SITE-SOP.md Part 0) — confirm the design is an SW1-supported variant or completed design-pack port. If it isn't, stop and flag it rather than quietly building a static stand-in. Chadstone Redbacks (Jul 2026) shipped weeks of static "gameday" build on an unported design before this was caught.

🔴 SEO/AEO (sitemap.xml, robots.txt, llms.txt, favicon, JSON-LD, Twitter Card) must be built per-club and dynamic — see SPORTSWEB-EDITABLE-SITE-SOP.md Part D's SEO/AEO subsection. Citing standards S4/S5/S6/S11 isn't enough; the same tenant shipped weeks without any of this until asked for explicitly (Chadstone Redbacks, Aug 2026).

Use this when you're building a new site (new design, new structure) — not replicating one existing site. Two things are decided independently: where the content comes from, and where the design comes from. Pick one option on each axis.

Part A — Two axes, decided separately

Axis 1 — CONTENT source

  • Old site exists → harvest it (do not re-key by hand). Use the Claude-in-Chrome technique (MIGRATE-FROM-EXISTING-SITE-PROMPT.md §2–§3): render each page, get_page_text, scroll + sweep the DOM/network for images across all hosts. Mine every real fact into CONTENT-BRIEF.md. Then improve it (S2): for each service/page seek real experience, credentials, process, pricing factors, proof — log gaps as [CLIENT TO SUPPLY]. Never invent.
    • SEO carry-over (MUST): an old site — even on a rebrand or new domain — has earned URLs. Inventory them and build the 1-to-1 301 map so equity transfers. Follow the Migration SOP's Phase 0 + Phase 5 for the cutover. A fresh design is not an excuse to drop rankings.
  • No old site → work from a client brief. Capture what they give you into CONTENT-BRIEF.md; everything unknown is [CLIENT TO SUPPLY], clearly marked. Ship honest placeholders, never fabricated facts/testimonials/stats (S1).

Axis 2 — DESIGN source

  • Replicate one live site → mirror that site's design system (read its CSS: tokens, type, spacing, breakpoints) and rebuild it clean. One direction, not variations.
  • Inspiration from N reference sites → open each, capture what works (layout patterns, type pairing, colour mood, section ideas), then synthesise a NEW design system — don't 1:1 copy any one of them, and never lift a competitor's brand, logo, or copyrighted assets. Record the derived tokens/type/layout in CONTENT-BRIEF.md before building.
  • From screenshots → the client sends images of sites/looks they like. Read them (vision): extract palette (sample the hex), type feel, layout, mood; name the design system from them. Ask for the source URL when the screenshot is partial (galleries/hover states aren't in a still).
  • From the brand itself → derive the palette from the logo (colour-count the PNG) + any existing collateral; pick fonts that match the sector tone (business playbook §C3).

These combine freely: e.g. content harvested from the old site + design synthesised from three inspiration sites the client screenshotted.

Part B — Process

  1. Capture design sources first — replicate target, inspiration sites, or screenshots → derive a design system (4–6 colours, 2–3 type roles, layout concept). Record it.

  2. Build CONTENT-BRIEF.md from the content source (old-site harvest or client brief); flag conflicts + gaps, never invent (S1/S2).

  3. If an old site exists: run Migration Phase 0 (URL inventory + 301 map skeleton) in parallel — see SPORTSWEB-LIVE-MIGRATION-SOP.md.

  4. Build to the standards — real multi-page (or the deliberate single-page option, Part C), per-page SEO + connected JSON-LD (S4/S5), llms.txt (S6), local/maps (S7), media budgets (S8), a11y (S13), perf (S14), real CTAs (S12). Build it editable (default): load the content into the club's editable fields through the admin Import a club / Site Migrations tooling, per SPORTSWEB-EDITABLE-SITE-SOP.md (content is served back out through the shared app's PageRenderer, publish-gated, don't invent tables/columns/content keys). Content the model has no home for yet ships as static fallback (S18) — extend the model, don't hardcode. Share a draft preview (?preview=<token>, noindex) for review — there is no separate preview deployment to stand up.

    🚦 GATE 4→5 — Codey STOPS here and waits for an explicit human GO. This is the only signal that moves the build to deploy. After the preview, Codey does not advance on its own judgement. It stays in a review loop: the reviewer (the super-admin/Carson OR the SportsWeb manager) checks the preview on desktop and mobile and states exactly what to fix in plain words; Codey applies each fix and re-shows — repeating until the reviewer is happy with the fixes. Then — and only after they're happy with the fixes — the reviewer types the exact words “Let’s go to step 5 — deploy / go live.” Those words are the only thing that advances it. The build is finished when the reviewer says so, never when Codey thinks it looks right. No deploy, publish, or cutover before that word. (Exception unchanged: flipping DNS on a live domain in step 5 needs Carson’s OK specifically — the one irreversible action.) ⚠ Numbering note for Codey — obey the ACTION, not the bare number. The reviewer's step numbers come from the human guide's flow and will not match the step numbers in any runbook you generate. Interpret a GO by its stated action — "deploy / go live" — never by matching the number to a same-numbered step in your own working list. If the reviewer gives a bare number with no action, confirm the action in one line before doing anything. Capture-the-fix rule: when the reviewer flags the same class of issue more than once, Codey must write that fix back into this SOP / the standards / the build prompt (a design token, a content rule, a QA line) so the next build doesn't repeat it — the reviewer should prompt for this, and Codey should offer it. Recurring manual corrections mean the prompt is missing a rule.

  5. Draft preview noindex (S10) → only after the GATE above → publish the club (the editor's "Publish site" / set_website_status RPC) so public reads serve the published layout → if the club needs its own custom domain, attach it: (a) add the domain to the SW1 Vercel project (there is only one project for the whole platform — no new project per club), (b) insert its club_domains row (host → slug, per src/lib/supabase.ts) so the app resolves it to this club → submit sitemaps (S16) → (if replacing an old site) cut over with the 301 map (S9). You run the DNS change with Carson's OK — Codey never touches a live domain.

Part C — Single-page vs multi-page

Small businesses/trades sometimes want a one-pager. Allowed, deliberately: build the standard sections as anchor blocks on one route, but keep every essential fact in real HTML (not only widgets), real mailto:/tel: CTAs (S12), and — if it replaces an old multi-URL site — 301 the old server-visible URLs and keep matching section ids so old fragment links still land (S9). Default to genuine multi-page (S3) where the business has enough real content for it.

Part D — Guardrails

Never invent content, logos, testimonials, credentials, reviews or stats (S1). Never clone a competitor's brand/site — inspiration is patterns, not assets. Never touch a live domain/DNS without sign-off. If replacing a live site, the earned SEO is a first-class deliverable — inventory + 301 it (S9), don't lose it.
