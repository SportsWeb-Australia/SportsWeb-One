SportsWeb One — Live-Site Migration SOP

Migrate an EXISTING live club website's content into SportsWeb One without losing earned traffic or rankings — the club then edits it through the platform editor.

Law is SPORTSWEB-WEB-STANDARDS.md (S1–S20) — on any conflict THAT file wins; this SOP only sequences the migration-specific execution the from-scratch SOP doesn't. Folds in the content/image-harvest technique from MIGRATE-FROM-EXISTING-SITE-PROMPT.md. Default end-state = the club onboarded into the existing SportsWeb One app (the club renders through the one shared app, content read via the public_club_page RPC and walked by PageRenderer.tsx; the owner edits through the platform editor) — the content model is defined once in SPORTSWEB-EDITABLE-SITE-SOP.md; this SOP reuses it, it does not re-invent it. There is no new repo and no new hosting decision — content is loaded into the existing app via the admin Import a club / Site Migrations tooling. Aug 2026.

Written for the Builder, not the Club Editor. This SOP is for Carson + Codey operating with full API/DB access to run a migration. It is not the guide a volunteer uses in the platform's Club Editor to maintain their own content afterwards.

Use this when: there is a live site with existing SEO equity / traffic to preserve (not a greenfield build). The prime directive is carry the earned rankings across the cutover — every ranking signal on the old site must be preserved or improved, and every indexed URL must resolve (200 or one-hop 301). Losing traffic on cutover is the failure mode this SOP exists to prevent.

🔴 Before you build anything, run the Pre-flight design check in SPORTSWEB-EDITABLE-SITE-SOP.md Part 0 — confirm the target design is an SW1-supported variant or a completed design-pack port. Chadstone Redbacks (Jul 2026) shipped weeks of static "gameday" build before anyone checked this; it wasn't supported. Don't repeat it.

🔴 SEO/AEO must be built per-club and dynamic, not hand-written once — SPORTSWEB-EDITABLE-SITE-SOP.md Part D's SEO/AEO subsection covers /sitemap.xml//robots.txt//llms.txt resolved by host, favicon, JSON-LD, Twitter Card. Especially load-bearing on a migration: this SOP's whole point is protecting earned rankings, and a missing per-club sitemap/schema undermines that even when the redirect map (S9) is perfect.

Part B — The migration spine (Phase 0 → 7). Each phase gates the next.

Phase 0 — SEO baseline & forensics (BEFORE touching or building anything)

You cannot preserve what you haven't measured. Produce MIGRATION-BASELINE.md:

  • Full URL inventory — union of: a scripted/browser crawl of every internal <a>, the old sitemap.xml, robots.txt, and (if given) GSC Pages/Coverage export + GA top landing pages. Add a backlink-tool export or site: sweep for pages other sites link to. This list is the authority for the 301 map — an indexed URL missing here becomes a lost-traffic 404 at cutover.
  • Per-URL snapshot (table): old URL · current <title> · meta description · <h1> · canonical · word count · existing JSON-LD types · inbound-link/traffic weight (if known) · → new route · 301?. High-traffic / high-backlink URLs are must-preserve; sort by weight.
  • Ranking + query baseline (if GSC/GA): top queries, top landing pages, current positions, monthly clicks — the yardstick you'll re-check post-cutover (Phase 7).
  • Existing structured data, NAP, GBP: capture current schema, and the exact Name/Address/Phone as shown on the site AND on the Google Business Profile — they must stay identical (S7).
  • Existing redirects & canonical host: current www/non-www, http→https, trailing-slash policy — preserve the canonical choice unless there's a reason to change (a host change is itself a migration).

Phase 1 — Content & image harvest via Claude-in-Chrome (S1/S2)

Builder/Wix/SITE123/TeamApp sites are JS-rendered — curl/WebFetch return almost nothing. Use the in-app browser:

  • Content → open each page, get_page_text; mine every hard fact into CONTENT-BRIEF.md (services, story/bio, testimonials with real names, projects, pricing, hours, contact, socials, service areas, acknowledgement). Never invent — gaps → [CLIENT TO SUPPLY] (S1). Flag every old-vs-new conflict, never silently pick (S2).
  • Load it into the platform (this is what makes the site editable). Seed the harvested facts into the SportsWeb One editable fields / content keys, via the admin Import a club tool where it fits, and directly through the content schema in SPORTSWEB-EDITABLE-SITE-SOP.md for the rest — do NOT invent tables/columns/keys — so the owner can edit every one of them after launch. Content the editable model has no home for yet ships as static fallback (S18) so nothing is lost — extend the model later rather than hardcoding. Net: the migrated content is both correct on day one and owner-editable.
  • Images → they're injected by JS from CDNs, not in the HTML. Render + scroll the page through (small synchronous scrollTo steps), then sweep the DOM for real URLs across all hosts (img.currentSrc||img.src + computed background-image); read_network_requests filtered to image types is the fallback. curl the URLs. Gallery/lightbox full-size images load from an async API and often can't be scraped — if a key photo is stuck there, ask the client; never fabricate or substitute someone else's photo. Genuine gaps → styled brand placeholder, clearly a placeholder.
  • Re-process every image to the S8 media budget (AVIF/WebP, width/height, hero ≤200 KB, descriptive filenames, real alt).

Phase 2 — Onboard the club into SportsWeb One as an editable tenant

  • Match (or apply the chosen new) design against an ALLOWED_VARIANTS entry (Part 0 pre-flight check, SPORTSWEB-EDITABLE-SITE-SOP.md); cleaner, faster, accessible, genuinely multi-page. There is no new codebase to write — the club renders through the existing shared SW1 app.
  • Editable, database-driven — load content per SPORTSWEB-EDITABLE-SITE-SOP.md's content model: seed the harvested facts into the club's content keys / editable fields (RLS-gated public reads, published-gate). The app holds no per-club editing UI and the migrated content never writes on its own — editing happens in the platform editor. Do NOT bake editable content into components; do NOT invent tables/columns/keys.
  • Per-page SEO/schema per the standards: unique title + meta + self-referencing absolute canonical + OG/Twitter + the page's JSON-LD (S4), served per-club and dynamically per SPORTSWEB-EDITABLE-SITE-SOP.md's SEO/AEO subsection (/sitemap.xml, /robots.txt, /llms.txt resolved by host); minimal client JS (S14).
  • Connected JSON-LD graph with stable @ids (S5): WebSite + WebPage/page + the most specific LocalBusiness/Organization subtype + Person + Service + BreadcrumbList; no self-serving AggregateRating on the business. Mark up only visible content; AU phone +61….
  • llms.txt + facts in real HTML (S6); S12 CTAs (no href="#", real mailto:/tel: until endpoints supplied); WCAG 2.2 AA (S13).

Phase 3 — SEO parity gate (the "don't lose rankings" checklist — MUST pass before cutover)

For every must-preserve URL from Phase 0:

  • A new route exists whose title, <h1>, and content depth are equal or better than the old page (thin→thin is a fail — improve per S2).
  • It's in the 1:1 301 map (old→new, permanent, one hop). Keep the same slug where sensible so no redirect is even needed; where the URL must change, 301 it. Fragment-only legacy links: keep the same section id + 301 the server-visible query variants (S9 fragment rule).
  • Internal links that pointed at the old page now point at the new canonical (no chains).
  • Schema, canonical, and NAP carried over. Zero orphans; key pages reachable without JS ≤3 clicks (S3).
  • Assets are NOT redirected; every 301 target returns 200, not another redirect.

Phase 4 — Staging, review & indexation control (S10)

There is no separate staging deployment — share the club's draft preview (/?preview=<token>, the editor's "Share draft for review", per SPORTSWEB-EDITABLE-SITE-SOP.md Part C): the club stays draft (website_status) so it renders noindex,nofollow, is out of sitemap.xml, and is invisible to the public until published. The draft preview must NOT compete with the live domain while it's still serving the old site.

🚦 GATE — Codey STOPS here and waits for an explicit human GO before Phase 5. This is the only signal that moves the draft preview to cutover. Codey does not advance on its own judgement. It stays in a review loop: the reviewer (the super-admin/Carson OR the SportsWeb manager) opens the draft preview, checks it on desktop and mobile and against the Phase 3 parity list, and states exactly what to fix in plain words; Codey applies each fix and re-shows — repeating until the reviewer is happy with the fixes. Then — and only after they're happy with the fixes — the reviewer types the exact words “Let’s go to Phase 5 — cut over (go live).” Those words are the only thing that advances it. The rebuild is finished when the reviewer says so, never when Codey thinks it looks right. No cutover before that word. And because Phase 5 flips DNS on a live domain, the go-live itself needs Carson’s OK specifically — the one irreversible action. ⚠ Numbering note for Codey — obey the ACTION, not the bare number. The reviewer's step numbers come from the human guide's flow (…preview → cut over / go live → post-launch watch) and will not match the step numbers in any go-live runbook you generate. Interpret a GO by its stated action — "proceed to cut over and take the site live" — never by matching the number to a same-numbered step in your own runbook (e.g. don't read "step 8" as "write the monitoring plan"). If the reviewer gives a bare number with no action, confirm the action in one line before doing anything. Capture-the-fix rule: when the reviewer flags the same class of issue more than once, Codey must write that fix back into this SOP / the standards / the build prompt (e.g. a design token, a content rule, a QA line) so the next build doesn't repeat it — the reviewer should prompt for this, and Codey should offer it. Recurring manual corrections are a signal the prompt is missing a rule.

Phase 5 — Cutover runbook (Carson executes DNS; Codey prepares everything)

  • Never change DNS/registrar yourself — hand Carson the exact records.
  • Same domain (SEO-safest, default): point the domain at the shared SW1 app — add it to the one SW1 Vercel project and insert its club_domains row (host → slug); ship the 301 map via vercel.json redirects on that same project; flip noindex → index,follow; real robots.txt (allow + sitemap ref); production sitemap.xml; publish the club (set_website_status RPC) so public reads serve the published layout. No GSC Change-of-Address needed (host change only).
  • New domain: all of the above plus GSC Change of Address from old→new property, and keep the old domain live serving the 301s (don't drop it) so equity transfers.
  • On go-live: verify the property in GSC + Bing Webmaster, submit the sitemap to both, IndexNow ping; confirm a sampled set of old→new returns HTTP 301, canonicals return 200, and the branded 404 renders for anything unmapped (S9/S16).

Phase 6 — Google Maps / local presence (S7)

  • Google Business Profile: confirm it's claimed; make the NAP identical to the site and schema; update the GBP website link to the new URL; align categories/hours/service-area.
  • On-site: LocalBusiness subtype + areaServed + AU phone in schema; an embedded Google Map + directions on Contact; address privacy for home/service-area businesses (expose areaServed, hide street). Only build a genuine location page where real local evidence exists — no thin suburb pages.

Phase 7 — Post-cutover watch (S16) — the proof equity transferred

For 2–4 weeks after go-live, monitor and fix regressions: GSC index coverage + crawl errors, 404s, the query/landing-page positions vs the Phase 0 baseline, Core Web Vitals, schema errors, broken links. A ranking dip that doesn't recover = investigate the 301 map / parity, don't wait. Tag which monitoring steps are candidates to automate inside the platform (S16/S18).

Part C — Verification before "done"

Run the full SPORTSWEB-WEB-STANDARDS.md end-checklist (S1–S20) plus the migration gate:

  1. MIGRATION-BASELINE.md exists — complete URL inventory + per-URL SEO snapshot + 301 map.
  2. Every must-preserve URL → a parity-or-better new page (Phase 3), all in the 1:1 301 map.
  3. Sampled old→new returns 301; no chains/loops/soft-404s; canonical targets 200; assets not redirected (S9).
  4. Draft preview is noindex,nofollow + out of sitemap + robots Disallow until the club is published (S10).
  5. Connected JSON-LD graph validates; no self-serving AggregateRating (S5).
  6. GBP NAP == site == schema; new URL set in GBP; map embed + areaServed present (S7).
  7. Go-live runbook prepared: DNS records for Carson, sitemap submit (GSC+Bing), IndexNow, Change-of-Address IF new domain.
  8. Post-cutover monitoring plan documented against the Phase 0 baseline.

Part D — Deliverables

The club onboarded into the existing SportsWeb One app — no new repo, no new host project — content loaded into the platform's editable fields, the owner can edit every one (the editable test passes: edit in the editor → publish → refresh → change shows) · MIGRATION-BASELINE.md (inventory + 301 map) · CONTENT-BRIEF.md · draft preview URL (noindex) · the DNS + go-live runbook for Carson · post-launch watch list. Never touch the live domain/DNS without sign-off.
