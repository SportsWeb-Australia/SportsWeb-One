Standard Operating Procedure · Editable Site (build)

Build a site the client edits themselves — through the platform, not the code.

A database-driven Astro site that reads the SportsWeb One / Business One database and renders it. The platform editor writes the content; the site holds no editing UI and never writes. Edit in the editor → publish → the site reflects it on the next request.

◆
The one rule that makes it work. Read from the same tables, columns and content-keys the editor already writes — never invent your own, never hardcode editable content. Static config is the fallback only. Break the contract and the site stops being editable.

ELI12 In plain English

  1. The site reads its words from a shared box (the database). Nothing is baked in.
  2. We only use the box's existing labels. Never invent new ones — that breaks the editor.
  3. If a label's empty, the site shows tidy default text — so it always looks finished.
  4. We build the pages properly — fast and findable.
  5. Nothing shows to the public until someone hits Publish. Until then it's private.
  6. Result: the club or business edits their own site in the editor — no code.

READ The read contract

All reads are .eq('club_id', CLUB_ID) and, for content tables, .eq('status','published'). Column spellings are British — primary_colour / secondary_colour / tertiary_colour.

GATE The publish gate — the #1 gotcha

!
Every public-read RLS policy on clubs / news / sponsors / events / teams / club_content requires clubs.website_status = 'published'. While the club is draft, the anon key reads nothing → the site correctly shows the static fallback. The editor's “Publish site” (the set_website_status RPC) flips it, and live data + every edit flow immediately.

So a freshly-built editable site looks complete (fallback) but isn't DB-driven for the public until published. There is no public_club_content RPC — the public path is direct selects gated by that RLS. A no-login draft preview is available at /?preview=<token> (“Share draft for review”).

HOW Architecture — Business-One-ready

SSR

Astro server-rendered, host-swappable

  • output:'server'; adapter per host (@astrojs/vercel or @astrojs/cloudflare).
  • Runtime-neutral data layer: @supabase/supabase-js with persistSession:false, autoRefreshToken:false (no localStorage/timers) → runs on Cloudflare Workers unchanged. A host swap is one adapter line.
DB

DB-first, static fallback

  • A loadClub() reads the tables/keys above and merges onto a static config; anything the DB hasn't supplied falls back to the static value, so the site is always complete.
  • Brand colours injected on <html> as --club-ink/paper/accent/silver; data-variant selects the surface mapping. Reuse the platform tokens/base/blocks CSS where the design must match.
  • Per-page SEO + connected JSON-LD per the standards (S4/S5/S6).

MEDIA Images / storage

  • Bucket club-media (public read); path {clubId}/{folder}/{filename}; folders: hero, brand, people, about, footer.
  • Image values in club_content and the content tables are already full public URLs — just render them. The site never uploads; the editor handles that.

STOP Do NOT (keeps the editor compatible)

  • Create new tables or rename columns.
  • Invent new content_key names or change existing ones.
  • Change the storage bucket or path convention.
  • Hardcode editable content into components.
  • Build editing UI — that stays in the platform.

CHECK Verify before “done”

  • Every page renders from Supabase (published rows); static fallback where the DB is empty.
  • The editable test: edit a value in the editor → Publish → refresh → the change shows. (While draft, the fallback is correct.)
  • Images load from club-media URLs; zero emoji; internal links resolve; production 200s; branded 404.
  • Runtime-neutral loader confirmed (no window/localStorage/Node built-ins) — host is swappable.
