SportsWeb One — Editable Site SOP (build)

Load a club's content into the shared SportsWeb One app so it's edited through the platform editor — not code.

Sibling to SPORTSWEB-LIVE-MIGRATION-SOP.md. Law = SPORTSWEB-WEB-STANDARDS.md (S1–S20). No club has been built end-to-end on F2/PageRenderer yet — "no club is live" (docs/F2-design-doc.md §10), only Carson's own demo estate. The Dookie United build predates this SOP's architecture (a standalone repo, not this shared app) and is not a valid reference anymore. The first real build against this SOP should become the reference — update this line once it exists.

Use this when the client will manage their own content over time. The club's site reads through the shared SW1 app — PageRenderer.tsx walks the published_layout/draft_layout returned by the public_club_page RPC (usePublicClubPage.ts) — and the platform editor writes the club's content. There is no per-club codebase, no editing UI baked into a site, and no per-club deploy step. Result: someone edits in the editor → publishes → the site reflects it on the next request. (For a set-and-forget marketing site that isn't an SW1 club at all, use the static business playbooks instead.)

Written for the Builder, not the Club Editor. This SOP is for Carson + Codey operating with full API/DB access to onboard a club's content. It is not the guide a volunteer uses in the platform's Club Editor to maintain their own content day to day.

Part 0 — Pre-flight design check (do this BEFORE writing a single page)

🔴 Learned the hard way on Chadstone Redbacks (Jul 2026): a static gameday-design build shipped and stayed live for weeks before anyone checked whether "gameday" was an SW1-supported design at all. It wasn't — the platform only renders the frozen set of allowed variants in SportsWeb-One/src/content/allowedVariants.ts (currently heritage, broadcast, arena, classic, stadium, editorial, momentum, coastal), and Chadstone's design was unbuilt platform work, not a shippable option.

Before starting any build under this SOP:

  1. Open SportsWeb-One/src/content/allowedVariants.ts and confirm the target design/variant is in ALLOWED_VARIANTS — or is an already-completed design-pack port (check SportsWeb-One/docs/ for a matching audit doc, e.g. rdca-port-audit.md).
  2. If it is neither — the design is bespoke, unported, or "planned/next" — stop and flag it to the client before writing any code. Do not quietly build a static stand-in as a placeholder; a static build has a habit of silently becoming the de facto deliverable. Get an explicit decision: wait for the platform port, pick an existing supported variant, or knowingly ship static with a documented follow-up to migrate later.
  3. Only once the design is confirmed supported (or the client has explicitly chosen a fallback) do you proceed to Part A.

Part B — The content model (do NOT change — the editor depends on it)

🔴 club_content (key/value) is the legacy path, being absorbed into the layout document under F2 — per docs/F2-design-doc.md, its public read "folds into [public_club_page] when F2 lands." Don't write new page-content fields to club_content; they belong in the layout document's section props instead (the registry's Content class — see docs/F2-design-doc.md §4).

The other tables below are the registry's Collection class — real typed tables that both the legacy renderer and F2 read directly, independent of the layout-document walk. usePublicClubPage.ts's "no direct table access" claim is about the page layout read specifically (one RPC, no ad-hoc queries for section content) — it does not mean collection data has no table of its own:

Content is written to these tables, all keyed .eq('club_id', CLUB_ID) and, for content tables, .eq('status','published') when read directly (e.g. by admin tooling): clubs · news (order published_at desc) · events (upcoming by event_date) · sponsors (order display_order) · teams · matches (order match_date) · ladder (order position) · people (committee: is_public=true only).

Column spellings are British: primary_colour / secondary_colour / tertiary_colour.

Storage

Bucket club-media, path {clubId}/{folder}/{filename}; folders in use: hero, brand, people, about, footer. Content-table + club_content image values are already full public URLs — just render them. The site never uploads.

Part C — The publish gate (CRITICAL — the #1 gotcha)

Every public-read RLS policy on clubs/news/sponsors/events/teams/club_content requires clubs.website_status = 'published'. While the club is draft:

  • the anon/publishable key reads nothing → the site correctly renders the static fallback;
  • the editor's “Publish site” button (the set_website_status RPC) flips draft → published, and live DB data + every editor change flow immediately.

So a freshly-onboarded club looks complete (fallback) but isn't yet DB-driven for the public until the club is published. Per usePublicClubPage.ts, the public read path is the public_club_page RPC (see the Part B marker above re: how this squares with the direct-select description elsewhere in this doc) — it returns published_layout for a published club, draft_layout for a valid preview token, otherwise zero rows (existence is never leaked). A shareable no-login draft preview is available at /?preview=<token> (the editor's "Share draft for review").

Part D — Architecture (grounded in docs/engineering-conventions.md)

  • One shared app, not one per club. Every club renders through sportsweb-one-club-template (Vite + React + TypeScript, react-router-dom). There is no per-club Astro build, no per-club SSR, no per-club Vercel/Cloudflare project — see engineering-conventions.md §1.
  • Domain resolution: src/App.tsx resolves which club to render from the request's domain; a club's custom domain never reaches a separate deployment, it renders that club's homepage inside the one app.
  • Single data entry point: usePublicClubPage.ts calls the public_club_page(club_id, slug, preview_token) RPC — no direct table access from the client renderer.
  • Rendering: PageRenderer.tsx walks the returned layout document against a section registry; a per-section error boundary means one broken section is skipped, never a white screen.
  • Colours injected on <html> as --club-ink/paper/accent/silver from the clubs row; data-variant selects the surface mapping. Reuse the platform tokens/base/blocks CSS where the design must match.
  • Onboarding a new club is a database row + content import through SiteMigrations.tsx / Import a club in the admin panel — never a new codebase, never a new deployment.
  • Per-page SEO/schema/etc. per the standards (S4/S5/S6).

SEO/AEO — the concrete build requirement, not just the standard

S4/S5/S6/S11 aren't satisfied by hand-writing tags once — on a multi-tenant platform they must be generated per club, dynamically, or every tenant silently ships without them. Build ALL of these before calling a tenant "done" (learned the hard way on Chadstone Redbacks, Aug 2026 — none of this existed until asked for explicitly):

  • /sitemap.xml, /robots.txt, /llms.txt — resolve the requesting club by host (custom domain → club_domains; {slug}.sportsweb.com.au; ?club= override for platform-host testing), then list that club's real pages + published news/team/event slugs. robots.txt must declare Sitemap: https://<host>/sitemap.xml using the request's own host — a static file can't do this for a multi-tenant app.
    • This app is the Vite/SPA case, not an edge-function/SSR framework: a catch-all SPA rewrite (/(.*) → /index.html) swallows these paths before your function ever runs — add explicit earlier rewrites entries pointing /robots.txt//sitemap.xml//llms.txt at their real /api/... function paths. And if package.json has "type": "module", api/*.js functions MUST use import/export default, not require/module.exports — CommonJS syntax there throws FUNCTION_INVOCATION_FAILED at runtime, not build time, so it looks fine until someone actually hits the route.
  • Favicon — set from the club's own logo once resolved, not the platform default. Non-trivial on a client-rendered app (index.html ships neutral platform defaults before the club resolves) — upsert link[rel="icon"]/link[rel="apple-touch-icon"] once the club's identity.logo is known.
  • JSON-LD — at minimum sport, address (or areaServed), telephone, sameAs (verified social URLs) whenever the underlying data exists — not just name/url/logo. Use the identity.location/identity.sports content-key overrides above so this doesn't block on a schema migration (e.g. a missing sport_type enum value).
  • Twitter Card — twitter:title/twitter:description/twitter:image alongside twitter:card, not just the card type alone.
  • og:image — a real photo (ideally 1200×630, per S8), not just the logo. Overridable per club/page via seo.image / seo.{page}.image.
  • Alt text — meaningful content images (news, team, gallery photos) get real descriptive alt text; empty alt="" is reserved for genuinely decorative images (hero watermarks, background motifs).

Part E — Do NOT

Create new tables · rename columns · invent content_key names · change the bucket or path convention · hardcode editable content into components · build editing UI (that stays in the platform).

Part F — Verify before "done"

  1. Every page renders from Supabase (published rows), static fallback where the DB is empty.
  2. The editable test: edit a value in the platform editor → Publish → refresh the site → the change shows. (While draft, expect the fallback — that's correct.)
  3. Images load from club-media URLs. Zero emoji; internal links resolve; 200s on production; branded 404.
  4. /sitemap.xml, /robots.txt, /llms.txt fetched directly (not through the app) and confirmed they return real per-club content — not a framework/SPA fallback page with a 200 status (the classic silent-failure mode).
  5. Favicon is the club's own crest; og:image/twitter:image is a real photo; JSON-LD has sameAs/address/sport wherever the data exists.
